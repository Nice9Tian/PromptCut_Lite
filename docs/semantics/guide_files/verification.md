# 验证

基线由哪几项组成、什么改动必跑哪一项、在哪里验。索引见 `../README.md`。

## 基线

| 项 | 命令 | 通过标准 | 什么时候必跑 |
|---|---|---|---|
| 类型检查 | `npx tsc -b --force` | 零错误 | 每次 |
| 构建（含类型检查） | `npm run build` | 成功 | 每次：提交 PR 前、合入 main、发版 |
| 测试 | `npm test -- <文件...>` | 零失败 | 每次：只跑这次改动影响到的那些测试文件（2026-10-23 用户定） |
| 全量测试 | `npm test` | 零失败 | **只在发版前**跑一次（2026-10-23 用户定；原先是每次都跑） |
| 导出确定性 | `node scripts/verify-determinism.mjs --url "http://127.0.0.1:5203/?export=1"` | 同一段导两遍，逐像素相同 | 日常合入 main 时改到画面，以及发版时（范围见下「按改动范围验证」） |
| 导出与快照重放一致 | `node scripts/verify-unified-frames.mjs` | 整条通过 | 日常合入 main 时改到快照、预渲染、渲染，以及发版时（范围见下「按改动范围验证」） |
| 画面 | 看图，或跑 `scripts/probes/` 下对应的探针（用法见各脚本文件头） | 画面正确、探针全过 | 改到用户看得见的画面 |

渲染附加项（G0-R）四项里，上表只收了「导出确定性」和「导出与快照重放一致」；另外两项「与 main 的像素比对」「预渲染探针」的命令和标准在 `../../plan/Master-Execution-Plan.md` 第 8 节。

**只跑受影响的那些（2026-10-23 用户定）**：每次改动不再跑全量，只跑这次改到的东西牵动的测试文件。怎么算「牵动」：自己改的文件本身的测试、引用了这些文件的测试、以及这次改到的那几条用户能看见的行为对应的测试；宁可多带几个文件，也不要漏。跑法仍然是 `npm test -- <文件...>`（必须经 `npm test`，它的全局 setup 占住端口，直接 `node --test` 跑要端口的测试会不准）。全量 `npm test` 改成发版前跑一次；发版前那一次仍然要零失败，它同时是 `release` 分支的合入门槛，发版记录照 `git_and_release.md` 办。

## 按改动范围验证（2026-10-06 用户定）

- **日常合入 main 时**，渲染附加项（导出确定性、快照重放、与 main 的像素比对、预渲染探针，即主计划第 8 节的 G0-R）只在改到**画面**时跑（发版合入 `release` 那一关整套必跑，见下节「PR、main、release 分别验什么」）：渲染管线、舞台、快照与预渲染、导出的取帧，或某张卡、某个部件的画面。
- 只改声音（混音、声音生成、音频素材、静音状态、卡片的 `audio()`）、或只改不出画面的逻辑时，不跑渲染附加项，改跑**覆盖自己范围的探针**，并验能不能听到、能不能导出有声成片。改动所属领域还没有自己的探针，就先补探针，验收标准写在探针文件头。
- 一次改动里夹着某张现有卡或部件的画面变化，只对**那几张卡**做改前改后逐帧比对（选能覆盖它全部参数分支的测试项目），不跑全量渲染附加项。像素基线的演示项目里没有这张卡时，全量比对测不到它，跑了也不算数。
- 拿不准算不算改到画面，按改到办。
- 改到素材长期缓存头（`server/asset-service.ts` 的缓存头、舞台路径号）要跑 `node scripts/probes/media-cache-probe.mjs`。它是真浏览器核对，不进 `npm test`，单测拦不住它查的那几类问题（2026-10-23 审查后补登记）。

## PR、main、release 分别验什么（2026-10-09 用户纠偏；2026-10-23 换成 PR / main / release 的说法）

- **提交 PR 前**：作者自己先过一遍，三项都要：`npm run build` 成功（它先跑类型检查，再 `vite build`）；本次改动影响范围内的测试零失败；本次改到的功能，其对应探针通过。跑过的探针，结果写成一个文件附在 PR 里，逐支列出文件名、命令和通过与否，不写「相关探针全过」这种含糊说法（2026-10-23 用户定）。见 `git_and_release.md`「提交」。
- **合入 main** 的门槛就是上面那三项在**合并后的状态**上全过（不是作者开 PR 时那一刻的状态）：`npm run build` 成功、影响范围内的测试零失败、对应探针通过。全量测试不在这一关（2026-10-23 用户改定：挪到发版）。按本次改动的范围验证，不让无关的历史探针挡住交付。**改到画面的改动，这一关还要跑渲染附加项**（导出确定性、快照重放、与 main 的像素比对、预渲染探针，范围按上节「按改动范围验证」判断）。
- **合入 `release`（即发版）** 才跑整套验收：全量 `npm test`、G0、G0-R、全部历史探针，加构建。G0 是通用门槛、G0-R 是渲染附加项，两者的项目、命令和标准在 `../../plan/Master-Execution-Plan.md` 第 8 节。发版这一关不看本次改动范围：无论这一版有没有改到画面，G0-R 整套都跑。
- 一个卡点查不出时，把问题与相关改动隔离到单独分支，已通过的其它成果照常合入。浏览器探针开工前先在基线提交上跑一遍留底：本来就不过的不算这次引入的，不挡别的 PR 合入；这次引入的，把相关改动留在分支上修。
- 失败、首次证据和复验数据保留到 `docs/archive/`；报告里只写结论和指向证据的路径。

## 耗时只记录，不当闸门（原「性能基准机」，2026-10-07 用户改定）

- 本节管发布验收闸门，不管软件的初始化测试闸门。舞台、素材、即时渲染等产品能力判断中的时间、性能界线和护栏继续生效，见 `../glossary.md`。
- **耗时不再决定过不过。** 验收项里的时间数字（编码耗时、加载与换档用时、握手用时、往返时延等）只记录，不作通过条件。原先「带耗时门槛的项以笔记本为基准机、在笔记本上过才算过、PC 上标待笔记本复核」的规则，以及同日早些时候定的「渲染五项在 PC 上限 4 核跑」，一并作废。
- **跟着发版记录。** 每次发版，把这些项在发版提交上跑一遍，把机器配置和各项耗时记进 `docs/reports/release-timings.md`，一个版本一节：版本号与提交、机器（哪台、处理器、核数、内存、显卡、系统）、各项的耗时数字。在哪台机器上跑都行，写明是哪台。
- **不看时间的断言照旧是通过条件**：功能对不对、黑帧数、透明拍数、长任务数、帧误差这类。
- **探针里的等待时限只为防卡死**：放宽到不会因机器快慢而误报；等到了头仍没有结果算这一项没跑出来，按不过处理。
- 别处文档里的「带耗时门槛」「待笔记本复核」「性能基准机」都按本节办。笔记本不再是任何一项通过的前提。
- 相邻两版之间某项耗时明显变差，在 `docs/reports/release-timings.md` 里标出来；不挡发版。

## 验证环境

- 验证另起一台 dev server，用 5203：`npm run dev -- --port 5203`。不用 5190～5192：5190 是日常开发那一台（`npm run dev` 的缺省端口），5191、5192 是它的舞台端口。
- 每台 dev server 另占「端口 +1」「端口 +2」当舞台端口，三个连号都要空着。

## 会造成真实损失的操作

- **worktree 里不要建 `node_modules` 的 junction、不要跑 `npm ci`**：worktree 建在仓库目录下（如 `.worktrees/`）时，Node 的依赖解析会自动向上找到主仓库的 `node_modules`，看起来「少了依赖」是正常的。建了 junction，清理 worktree 时会顺着链把主仓库的依赖清空。
- **删含 junction 的目录**：先在 PowerShell 里用 `[System.IO.Directory]::Delete('<junction 路径>')` 只拆链接，用 `Test-Path` 确认没了再删，确认失败就中止。不要在 Git Bash 里用 `cmd //c rmdir`。
